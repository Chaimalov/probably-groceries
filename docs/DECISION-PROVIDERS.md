# User-configured decision providers — issue #38

## First vertical slice

Settings → המלצות חכמות offers OpenAI Decisions (`gpt-6-luna`) and TypeSafe System One (`jev-latest`). Each adapter uses the provider's dedicated predicate/noul API, never chat/completions/Responses. There is no generic model field or speculative OpenRouter adapter. Alias/aisle/score tasks are future capabilities; this release implements replenishment predicates only.

Official contracts reviewed 2026-10-31:
- https://developers.openai.com/api/reference/typescript/resources/decisions/methods/create
- https://docs.typesafe.ai/api/system-one

These documents describe the wire contracts. Actual account access, inference quality and device behavior require an authorized user connection and real-device validation. No live credentials are available in the development environment, and no paid requests were made during development.

## Connection and execution

User-entered keys live in a device-only Keychain record. Connection first sends synthetic evidence to the selected fixed HTTPS endpoint, then saves the connection and enables decision recommendations on the current list. Changing providers replaces the connection and sponsors only the current list. UI discloses paid usage, shared purchase-history consent and direct-device execution. Existing Mercury matching settings remain for legacy lists; it stops matching lists using the new engine.

Each inference sends at most 32 eligible products with name (120 characters), unit (40 characters), and up to six recent purchases as elapsed whole days and quantity. Request-scoped labels replace product/CloudKit IDs. Notes, photos, emails and account IDs are excluded. Three distinct shopping trips are a conservative native eligibility requirement; local timing thresholds do not select the model's answers. Native code still owns quantities, alias suppression, active items and deferrals.

The adapters only accept bounded probabilities for known question labels. Unknown/duplicate labels, unexpected types/models and invalid ranges fail closed. Refused/missing answers produce no suggestion. The initial 0.85 selection threshold is a tunable policy, not measured precision. No generated rationale is shown.

Direct requests reject redirects, use an ephemeral session, have bounded deadlines and never log keys or provider error bodies. Limits: 20 requests/day/device including synthetic tests and failures; automatic refresh throttled to 15 minutes after a request and one-hour backoff after failure. Manual refresh still respects daily/backoff limits. This is not a provider-side financial cap. No automatic provider/payer fallback occurs.

## Shared results and failure behavior

A minimal result batch is persisted separately from shopping entities as `decision_<listID>` through the existing ShoppingEntity CloudKit journal. It contains list ID, source digest, time, provider, sponsor display name/installation ID and selected product IDs, never credentials. Existing journal conflict rules make concurrent results converge deterministically. A source digest and six-hour lifetime invalidate stale proposals; native suppression runs again on consumption.

Recipients need no provider account. The sponsor device must be available to create fresh results. No remote proxy is deployed, no key is uploaded to our Worker and no continuous iOS background execution is promised. Real two-account convergence still needs device verification. Old binaries cannot consume the new entity; update all participants for this feature.

New-mode suggestions are hidden offline, including shared results. Existing manually added list entries keep working. Disconnect deletes the local credential and tombstones batches generated by that installation, preserving purchase history and accepted items. It does not revoke the API key at the provider. An in-flight result is discarded after disconnect/provider change, cancellation or source changes.

Unmigrated lists preserve the previous local predictor until the migration is accepted. A connected list never silently falls back after network/auth/quota failure or disconnect. Persistent preparation drafts retain edits; decision entries are shown/confirmed only while their product remains a valid online proposal. Fresh batches append new proposals without overwriting draft edits or exclusions.

## Validation / remaining release work

Domain tests cover wire validation, refusals, native suppression, cross-list scope, revision invalidation, backward decoding, CloudKit routing and tombstones. Local runtime has no Swift compiler; use the existing PR host-domain tests and unsigned iOS/watch compilation. These checks are not live provider or physical-device verification.

Before enabling on household devices: verify successful/denied connections on both providers, cancellation and credential replacement, offline check-off, corrected purchases, two-account shared results and privacy/retention disclosures for the chosen provider. The settings explanation is not a promise of zero provider retention. No production keys, billing, repository visibility, signing or TestFlight assignment are changed by this PR.
